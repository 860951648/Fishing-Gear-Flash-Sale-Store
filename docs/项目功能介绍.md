# 项目 A · 渔具秒杀商城 —— 功能介绍

> 本文回答“**谁**在**哪个模块**能做**什么**，以及**怎么实现的**”。
> 每个功能固定三段：`用户故事`（业务视角）→ `技术实现`（真实类名/关键代码路径）→ `涉及表 / 接口`（可直接对照 `sql/schema.sql` 与根目录 `接口文档.md`）。
> 怎么把项目跑起来见 [项目运行介绍.md](./项目运行介绍.md)。

---

## 1. 项目定位与角色

**定位**：钓场自营渔具的一次性秒杀交易系统。商品有多个 SKU 与库存；秒杀活动限时、限量；下单后 30 分钟不付自动关单；支付走本地模拟网关（不是真实微信/支付宝）；支付后可申请退款，运营审核。

**两个角色**（A 只有 `t_user` 一张用户表，没有独立角色表，运营权限按账号规则推导）：

| 角色 | 账号来源 | 权限码 | 能做什么 |
|---|---|---|---|
| 买家 `ROLE_USER` | 注册或种子数据 `buyer1` | 仅要求登录 | 商品浏览、秒杀下单、我的订单/详情/取消、模拟支付、申请退款、查自己的退款 |
| 运营管理员 `ADMIN` | 种子数据 `admin` | `product:manage`、`seckill:manage`、`order:manage`、`refund:audit`、`stats:view` | 商品/SKU/库存管理、秒杀活动创建与预热、全量订单、退款审核、运营看板 |

运营权限的判定链路：`PermissionServiceImpl#loadAuthorities(userId)` → 若账号是 `admin` 返回 5 个权限码，否则返回空 → 结果缓存 `trade:perm:{userId}`（5 分钟）→ `JwtAuthenticationFilter` 每次请求重建 `LoginUser.authorities` → `@PreAuthorize("hasAuthority('xxx')")` 校验。**JWT 里不放权限列表**，改权限只需删缓存。

## 3. 买家侧功能

### 3.1 认证：注册 / 登录 / 登出 / 当前用户

**用户故事**：作为买家，我希望能注册账号并用账号密码登录，登录后能一直用到 token 过期；如果我点了“退出登录”，旧 token 必须立刻失效，不能被人捡起来继续用。

**技术实现**

- 注册 `AuthServiceImpl#register`：`username` 查重（重复 409）→ `BCryptPasswordEncoder.encode` 只存摘要 → `status=1`。用户名不存在与密码错误返回**同一句**“用户名或密码错误”，避免被拿来枚举账号。
- 登录 `AuthServiceImpl#login`：`BCrypt.matches` 校验 → 读 token 版本号 `trade:auth:ver:{userId}` → 签发 JWT（payload 只有 `userId`/`jti`/`ver`）→ 写白名单 `trade:auth:whitelist:{jti}`，**TTL 等于 token 剩余有效期** → 返回 `LoginVO{token, tokenType, expiresIn, user, permissions}`。
- 每次请求 `JwtAuthenticationFilter`：解析 `Bearer` → 验签 → 查白名单是否存在 → 比对 `auth:ver:{userId}` 与 token 里的 `ver` → 加载权限 → 塞 `UsernamePasswordAuthenticationToken`。白名单缺失或版本号不一致 → 401。
- 登出 `AuthServiceImpl#logout`：删除当前 `jti` 的白名单 key，token 立即作废（这是 A 区别于“纯 JWT”的关键点）。
- Redis 故障：过滤器抛 `RedisConnectionFailureException` → `GlobalExceptionHandler` 返回 **503 + “认证服务暂不可用”**（fail-closed，不放行）。

**涉及表 / 接口**

| 接口 | 说明 | 表 |
|---|---|---|
| `POST /api/auth/register` | 公开 | `t_user` |
| `POST /api/auth/login` | 公开，返回 token | `t_user` |
| `POST /api/auth/logout` | 登录态，删白名单 | — |
| `GET /api/auth/me` | 登录态 | `t_user` |

### 3.2 商品浏览（列表 + 详情，Redis 逻辑过期）

**用户故事**：作为买家，我打开商品列表能分页、按名称搜；点进详情能看到 SKU 与实时可用库存。大促时很多人同时刷新同一个商品，不能把数据库打挂，也不能因为缓存过期就白屏。

**技术实现**

- 列表 `ProductServiceImpl#page`：`LambdaQueryWrapper` 过滤 `status=1`，`keyword` 同时模糊匹配 `name`/`subtitle`，分页由 `PaginationInnerInterceptor` 完成，返回 `PageResult`（不暴露 MP 的 `Page`）。
- 详情 `ProductServiceImpl#detail`：Redis Hash `trade:product:{id}`，字段 `data`（JSON）+ `expireAt`（毫秒）。
  - `expireAt > now`：直接返回缓存。
  - `expireAt <= now`（逻辑过期）：`SETNX trade:product:lock:{id}`（5 秒、value 为 UUID）抢重建锁；抢到的同步回源重建；**抢不到的直接返回旧值**（不阻塞用户）；`finally` 用 `unlock.lua` 比对 value 再删锁，避免误删。
  - 命中空值缓存（`data=""`，60 秒）：直接返回 404“商品不存在”——防穿透。
  - 物理 TTL 设成「逻辑过期 + 1 分钟」，兜底回收冷数据。
- 运营改价/改库存后调 `evictDetailCache` 删 key，避免前端看到旧价。

**涉及表 / 接口**

| 接口 | 说明 | 表 |
|---|---|---|
| `GET /api/products?page&size&keyword` | 公开，上架商品分页 | `t_product` |
| `GET /api/products/{id}` | 公开，含 SKU 与库存 | `t_product`、`t_sku`、`t_stock` |

Redis key：`trade:product:{id}`、`trade:product:lock:{id}`。

### 3.3 秒杀专区：活动列表与实时库存

**用户故事**：作为买家，我要看到“进行中/即将开始”的秒杀活动；活动详情里每个 SKU 的剩余量必须跟别人看到的一致，不能出现“页面显示有货、点下去没货”。

**技术实现**

- `SeckillServiceImpl#listActivities`：查 `t_seckill_activity`（按开始时间倒序），只返回进行中与未结束的活动，金额 `BigDecimal`。
- `SeckillServiceImpl#detail`：活动 + 关联 `t_seckill_sku` + `t_sku`/`t_product` 名称，**库存优先读 Redis** `trade:seckill:stock:{seckillSkuId}`；key 不存在（未预热）时回退 DB `t_seckill_sku.stock` 并提示运营预热。
- 与商品详情缓存分离：秒杀详情不复用 `trade:product:*`，因为秒杀库存变更频率远高于商品详情。

**涉及表 / 接口**

| 接口 | 说明 | 表 |
|---|---|---|
| `GET /api/seckill/activities` | 公开 | `t_seckill_activity` |
| `GET /api/seckill/activities/{id}` | 公开，含每个 SKU 的 Redis 实时库存 | `t_seckill_activity`、`t_seckill_sku`、`t_sku`、`t_product` |

### 3.4 秒杀下单（项目最核心链路）

**用户故事**：活动开始瞬间会有大量买家同时点“抢购”。我只能买到 1 件（一人一单），库存不能超卖；如果我这次没抢到，要立刻告诉我“已抢完”，不能让我等十几秒再报错。运营那边看到的库存数不能比实际多。

**技术实现**（`SeckillServiceImpl#seckill` → `OrderServiceImpl#createSeckillOrder`，四层防护）

0. **路径参数澄清**：`POST /api/seckill/{activityId}/skus/{skuId}` 里的 `skuId` 是 `t_sku.id`，服务里按 `(activity_id, sku_id)` 反查 `t_seckill_sku`；而 Redis 库存 key 用的是 `t_seckill_sku.id`（详情接口返回的 `skus[].seckillSkuId`）。两个 id 混用是排查秒杀问题最常见的坑。
1. **限流**：`rate_limit.lua` 令牌桶，key `trade:rate:{userId}:/api/seckill`，容量 20、10 个/秒（`app.seckill.rate-limit-capacity/rate`，默认 20/10），超限 429“操作过于频繁”。时间戳由 Java 传入（`System.currentTimeMillis()/1000` 作为 `ARGV[3]`），脚本只做“按流逝时间补令牌 + 扣令牌”的原子计算；代价是多实例部署时依赖各节点时钟一致（本项目单机演示，严格场景应改用 `redis.call('TIME')`）。
2. **Lua 原子预扣** `lua/seckill_deduct.lua`：一次脚本内完成「未预热判断 → 库存判断 → `SETNX` 一人一单幂等 → 扣减」，返回 `-1` 未预热 / `0` 库存不足 / `2` 重复下单 / `1` 成功。三段逻辑分开写就会并发读同一库存导致超卖，所以必须原子。拿到 `-1` 时服务端用 `SETNX` 从 DB 库存**自动回填一次**再重试，避免运营漏点预热导致整场卖不动。
3. **同步落库（事务）** `OrderServiceImpl#createSeckillOrder`：`@Transactional(rollbackFor = Exception.class)` 内做
   - `UPDATE t_seckill_sku SET stock=stock-1 WHERE id=? AND stock>=1`（`SeckillSkuMapper#deductStock`）
   - `UPDATE t_stock SET available=available-1, locked=locked+1 WHERE sku_id=? AND available>=1`（`StockMapper#deductOne`）
   - 插 `t_order`（`order_no=IdGenerator.orderNo()`，`status=0 待支付`，`version=0`）+ `t_order_item` + `t_stock_log`（`type=1` 扣减，`(order_no,type)` 唯一索引兜重复）
   任一步影响 0 行 → 抛 `BusinessException(409)`，事务回滚。
4. **失败补偿**：事务抛异常时 `SeckillServiceImpl#compensate` 把 Redis 库存 `INCR` 回来并删除该用户的幂等 key（不删的话他 24 小时都抢不了）；唯一索引 `(user_id, seckill_sku_id)` 是最后一道“一人一单”保险，`DuplicateKeyException` 也走同一补偿分支。
5. **不依赖 MQ 建单**：下单是同步完成的；MQ 只用于 30 分钟延迟关单（见 §5.5），生产者在 `app.mq.enabled=false` 时直接打日志返回，所以 RabbitMQ 没装也能完整演示。

**涉及表 / 接口**

| 接口 | 说明 | 表 |
|---|---|---|
| `POST /api/seckill/{activityId}/skus/{skuId}` | 登录 + 限流；返回 `{orderNo}` | `t_seckill_sku`、`t_stock`、`t_order`、`t_order_item`、`t_stock_log` |

Redis key：`trade:seckill:stock:{seckillSkuId}`、`trade:seckill:user:{seckillSkuId}:{userId}`、`trade:rate:{userId}:{path}`。

### 3.5 我的订单：列表 / 详情 / 取消

**用户故事**：作为买家，我能按状态筛选我的订单，点进去看明细；还没付款的订单我可以主动取消，取消后库存应该还回来。

**技术实现**

- 列表 `OrderServiceImpl#pageMine`：`LambdaQueryWrapper` 按 `user_id` 过滤 + `status` 可选 + `id DESC` 分页；本页订单明细**一次 `IN` 查出**再 `groupingBy`，避免 N+1。
- 详情 `OrderServiceImpl#detail`：本人或持 `order:manage` 才可看，否则 403；明细从 `t_order_item` 查。
- 取消 `OrderServiceImpl#cancel`：先校验状态必须为 `0 待支付`，再走幂等关单 `doClose`：
  - `OrderMapper#markClosed`（`UPDATE t_order SET status=4, close_time=now() WHERE order_no=? AND status=0`）CAS 抢单，影响 0 行说明已被支付/并发关单 → 409。
  - 抢到才回滚：`StockMapper#rollbackOne`（`available+1, locked-1`）、`SeckillSkuMapper#restoreStock`、Redis 秒杀库存 `INCR`（仅当 key 还存在，否则会凭空多库存）、删用户幂等 key，并写 `t_stock_log(type=3)`。

**涉及表 / 接口**

| 接口 | 说明 | 表 |
|---|---|---|
| `GET /api/orders?page&size&status` | 登录，只看自己 | `t_order`、`t_order_item` |
| `GET /api/orders/{orderNo}` | 登录，本人或运营 | `t_order`、`t_order_item` |
| `POST /api/orders/{orderNo}/cancel` | 登录，仅 `0` 可取消 | `t_order`、`t_stock`、`t_seckill_sku`、`t_stock_log` |

### 3.6 模拟支付（本地网关 + 回调幂等）

**用户故事**：作为买家，我在订单详情点“模拟支付”就能把订单变成已支付；支付网关可能会重复回调，重复回调不能让订单重复入账、也不能把已支付的订单改回未支付。

**技术实现**（`PaymentServiceImpl`）

- `POST /api/pay/mock/{orderNo}` 是本地模拟网关：按 `HMAC_SHA256(orderNo|amount|timestamp|nonce, app.pay.secret)` 生成 `sign`，然后**调用与真实回调同一个** `handleCallback/callback` 方法，演示环境和线上走同一条链路。
- `POST /api/pay/callback` 面向“外部网关”：先验签（`PAY_SECRET`，时间戳容差 300 秒防重放）→ 再入账。
- 入账链路：验签 → `SETNX trade:lock:pay:{orderNo}`（10 秒，value UUID，`unlock.lua` 释放）→ 查 `t_payment_record.channel_trade_no` 是否已处理（唯一索引）→ 订单状态机 `0→1` CAS（`WHERE status=0`）→ 写 `t_payment_record` → 解锁。
- 重复回调：唯一索引命中或 CAS 影响 0 行 → **直接返回成功**（幂等，不报错、不重复入账）。锁只减少并发，正确性由唯一索引 + 状态机 CAS 保证，Redis 主从丢锁也不会重复入账。

**涉及表 / 接口**

| 接口 | 说明 | 表 |
|---|---|---|
| `POST /api/pay/mock/{orderNo}` | 登录，本地模拟网关 | `t_order`、`t_payment_record` |
| `POST /api/pay/callback` | 公开 + 签名校验 | `t_order`、`t_payment_record` |

Redis key：`trade:lock:pay:{orderNo}`。

### 3.7 退款申请与我的退款

**用户故事**：作为买家，已支付/已发货/已完成的订单我可以申请退款并写理由；提交后订单进入“退款中”，我能看到审核进度和审核备注。

**技术实现**（`RefundServiceImpl#apply`）

- 校验订单归属与状态：只有 `1 已支付`、`2 已发货`、`3 已完成` 允许申请；订单状态 CAS `→5 退款中`，避免重复申请。
- 生成 `refund_no`（`IdGenerator`），金额取订单 `pay_amount` 并按 `HALF_UP` 保留 2 位，落 `t_refund`（`status=0 待审核`）。
- 我的退款列表按 `user_id` 分页，返回审核状态/备注。

**涉及表 / 接口**

| 接口 | 说明 | 表 |
|---|---|---|
| `POST /api/refunds` | 登录；返回 `{refundNo}` | `t_refund`、`t_order` |
| `GET /api/refunds?page&size` | 登录，只看自己 | `t_refund` |

## 4. 运营侧功能

### 4.1 商品 / SKU / 库存管理

**用户故事**：作为运营，我要新建商品（一次带多个 SKU 和初始库存）、改价格和副标题、调整某个 SKU 的可用库存、下架不再卖的商品。下架后买家列表里应看不到，但历史订单明细不能丢。

**技术实现**（`AdminProductServiceImpl`）

- 新增 `create`：`@Transactional` 内插 `t_product` → 逐个插 `t_sku` → 为每个 SKU 插 `t_stock`（`total=available=初始库存`，`locked=0`，`version=0`）；返回 `IdVO(productId)`。
- 编辑 `update`：SKU 有 id 走更新、无 id 走新增；金额统一 `setScale(2, HALF_UP)`；改完调 `ProductService#evictDetailCache` 删详情缓存（否则前端看到旧价）。
- 删除 `delete`：**逻辑删除**（`@TableLogic` 的 `deleted=1`），不物理删，保证历史订单明细还能显示商品名。
- 库存调整 `updateStock`：直接改 `t_stock.available`（运营补货场景），带 `@Version` 乐观锁，影响 0 行返回 409“数据已被修改”。
- 权限：类/方法上 `@PreAuthorize("hasAuthority('product:manage')")`。

**涉及表 / 接口**

| 接口 | 说明 | 表 |
|---|---|---|
| `GET /api/admin/products` | `product:manage`，含下架商品 | `t_product` |
| `POST /api/admin/products` | `product:manage`，含 `skus[]` | `t_product`、`t_sku`、`t_stock` |
| `PUT /api/admin/products/{id}` | `product:manage` | 同上 |
| `DELETE /api/admin/products/{id}` | `product:manage`，逻辑删除 | `t_product` |
| `PUT /api/admin/skus/{id}/stock` | `product:manage`，改可用库存 | `t_stock` |

### 4.2 秒杀活动管理与库存预热

**用户故事**：作为运营，我要建一个秒杀活动，选好参与的商品 SKU、定秒杀价和秒杀库存；活动开始前点一下“预热”，把库存刷进 Redis，否则买家抢购会报“未预热”。活动结束后不该有人还能抢。

**技术实现**（`AdminSeckillServiceImpl`）

- 创建 `create`：`@Transactional` 插 `t_seckill_activity` + `t_seckill_sku`（`unique(activity_id, sku_id)` 防重复配置），起止时间用 `LocalDateTime`，开始时间必须早于结束时间。
- 预热 `preheat`：把每个 `t_seckill_sku.stock` 写入 `trade:seckill:stock:{seckillSkuId}`（直接覆盖写，保证重新预热以 DB 为准）；**不额外设 TTL**——下次预热会覆盖旧值，`StockReconcileTask` 对账兜住残留，因此"活动结束后的旧 key"不会影响下一场（前提是运营新建/编辑活动后点一次预热）。
- 列表 `list`：运营视角返回全部活动（含未开始/已结束），带每个活动的 SKU 数、总库存。
- 权限：`@PreAuthorize("hasAuthority('seckill:manage')")`。

**涉及表 / 接口**

| 接口 | 说明 | 表 |
|---|---|---|
| `GET /api/admin/seckill/activities` | `seckill:manage` | `t_seckill_activity`、`t_seckill_sku` |
| `POST /api/admin/seckill/activities` | `seckill:manage`，含 `skus[]` | `t_seckill_activity`、`t_seckill_sku` |
| `POST /api/admin/seckill/activities/{id}/preheat` | `seckill:manage`，写 Redis | `t_seckill_sku` |

### 4.3 订单管理（全量查询）

**用户故事**：作为运营，我要看到全平台订单，按状态筛选，点进任意订单看明细（用于客服核对）。

**技术实现**：`OrderServiceImpl#pageAdmin` 与买家列表共用 VO 与“一次 IN 查明细”的写法，只去掉 `user_id` 过滤；详情接口复用 `OrderServiceImpl#detail`，持 `order:manage` 可越过归属校验。权限 `@PreAuthorize("hasAuthority('order:manage')")`。

**涉及表 / 接口**：`GET /api/admin/orders?page&size&status`（`t_order`、`t_order_item`）。

### 4.4 退款审核

**用户故事**：作为运营，我要看到待审核退款单，点通过就把钱退回去（订单变“已退款”、库存回补），点驳回要填理由并把订单退回原状态。

**技术实现**（`RefundServiceImpl#audit`）

- 只允许审核 `status=0 待审核` 的退款单（CAS 更新 `t_refund`，影响 0 行 → 409 已被他人审核）。
- 通过：订单状态 `5 退款中 → 6 已退款`（CAS，`WHERE status=5`）→ 回补 `t_stock.available` 与秒杀库存 → 写 `t_stock_log(type=2 退款回滚)` → 退款单置 `1 通过` + `audit_remark`。
- 驳回：退款单置 `2 驳回`，订单回到申请前状态（订单表 `remark`/原状态由业务字段记录，CAS `WHERE status=5`），库存不动。
- 权限 `@PreAuthorize("hasAuthority('refund:audit')")`。

**涉及表 / 接口**

| 接口 | 说明 | 表 |
|---|---|---|
| `GET /api/admin/refunds?page&size&status` | `refund:audit` | `t_refund` |
| `POST /api/admin/refunds/{id}/audit` | `refund:audit`，`{approved,remark}` | `t_refund`、`t_order`、`t_stock`、`t_stock_log` |

### 4.5 运营看板与销售趋势

**用户故事**：作为运营，我打开看板要看四个数：今日销售额、今日订单数、待审核退款、库存预警 SKU 数；再看近 7/30 天销售趋势，判断活动效果。

**技术实现**（`StatsServiceImpl` + `resources/mapper/StatsMapper.xml`）

- 复杂聚合写 XML、参数全 `#{}`：`selectSalesAmount`（`SUM(pay_amount)`，仅 `status IN (1,2,3)`，按 `pay_time` 归日）、`selectOrderCount`、`selectPendingRefundCount`（`t_refund.status=0`）、`selectStockWarnCount`（`available < 阈值`，默认 10）、`selectSalesTrend`（`GROUP BY DATE_FORMAT(pay_time,'%Y-%m-%d')`）。
- 服务层负责口径与补零：最近 N 天无数据的日期补 `0`，金额统一 `HALF_UP` 两位。
- 权限 `@PreAuthorize("hasAuthority('stats:view')")`。

**涉及表 / 接口**

| 接口 | 说明 | 表 |
|---|---|---|
| `GET /api/admin/stats/overview` | `stats:view` | `t_order`、`t_refund`、`t_stock` |
| `GET /api/admin/stats/sales-trend?days=7` | `stats:view` | `t_order` |

## 5. 横切设计（不属于某个页面，但每个功能都在用）

### 5.1 统一响应与异常分类

`Result<T>{code,msg,data}`；`ResultCode` 与 HTTP 对齐（200/400/401/403/404/409/429/500/503）。`GlobalExceptionHandler` 分类处理：`BusinessException`（原样 code）、`MethodArgumentNotValidException/BindException`（400 + 字段名）、`AccessDeniedException`（403）、`AuthenticationException`（401）、`RedisConnectionFailureException`（503）、`DuplicateKeyException`（409）、`Exception`（500，日志留堆栈、响应不暴露堆栈）。401/403 由 `RestAuthenticationEntryPoint` / `RestAccessDeniedHandler` 输出 JSON，不是 Spring Security 默认 HTML。

### 5.2 订单状态机（7 状态，全部 CAS）

`0 待支付 / 1 已支付 / 2 已发货 / 3 已完成 / 4 已关闭 / 5 退款中 / 6 已退款`。

允许流转：`0→1` 支付、`1→2` 发货、`2→3` 收货、`0→4` 超时/取消、`1/2/3→5` 申请退款、`5→6` 审核通过、`5→原状态` 驳回。
所有更新都是 `UPDATE t_order SET status=#{to}, version=version+1 WHERE id=#{id} AND status=#{from}`，影响 0 行返回 409——支付成功与超时关单并发时，谁先成功谁生效，另一个自然失败。

### 5.3 防重 / 幂等三道防线

| 场景 | 入口幂等 | 兜底 |
|---|---|---|
| 秒杀下单 | Redis `SETNX trade:seckill:user:{seckillSkuId}:{userId}`（24 小时，`RedisKeys.seckillUser`） | 唯一索引 `(user_id, seckill_sku_id)` |
| 支付回调 | Redis 锁 `trade:lock:pay:{orderNo}` + 状态机 CAS | 唯一索引 `t_payment_record.channel_trade_no` |
| 关单 | CAS `status=0 → 4` | 唯一索引 `t_stock_log(order_no, type)` 防重复回补 |

### 5.4 商品缓存三件套（穿透 / 击穿 / 雪崩）

- **穿透**：id 必须为正；查不到也缓存空值 60 秒。
- **击穿**：逻辑过期（热点 key 不物理过期）+ 重建互斥（`SETNX` 5 秒，抢不到返回旧值）。
- **雪崩**：商品详情的物理 TTL 设成"逻辑过期 + 1 分钟"，冷数据自然回收、也不会集中失效；活动开始前预热减少回源。

### 5.5 延迟关单：MQ 为主、定时任务兜底（两条路径同一个幂等方法）

- `app.mq.enabled=true` 时：`RabbitMQConfig` 声明 `order.delay.exchange → order.delay.queue`（`x-message-ttl=1800000`、`x-dead-letter-exchange=order.dlx`、`x-dead-letter-routing-key=order.close`）→ `order.close.queue`；`OrderCloseConsumer` **手动 ACK**，先插 `t_mq_consume_log`（`message_id` 唯一）幂等，再调 `OrderService#closeOrder`。
- `app.mq.enabled=false`（本机默认）：不建连接，只跑 `OrderCloseTask` 每分钟扫 `status=0 AND create_time < now-30min`（批量 100）。
- 两条路径调同一个 `OrderService#closeOrder` → `doClose`，重复投递/重复扫描都是幂等返回 false，不会重复加库存。
- `StockReconcileTask` 每天对账（Redis 秒杀库存与 `t_seckill_sku.stock` 差异告警/回补）。

### 5.6 限流

`rate_limit.lua` 令牌桶：key `trade:rate:{userId}:/api/seckill`，容量 20、速率 10/s、TTL 60 秒；时间戳由 Java 传入（脚本不调 `redis.call('TIME')`，单机部署下与 Redis 时间一致）；超限 429。只挂在秒杀下单这一个写热点上——限流不是为了拦人，而是为了不让热点接口把 Redis 和 DB 打满。

统一机制：

- `utils/request.js`：`baseURL:'/api'`、请求头 `Authorization: Bearer <token>`、`code!==200` 用 `ElMessage.error` 提示，401 清 token 跳 `/login?redirect=`，403/429 提示，HTTP 层错误走同一套文案。登录/注册接口的 401/400 不触发跳转，否则用户看不到“密码错误”。
- `store/user.js`（Pinia）：`token`/`user`/`permissions`/`roles`，`login()`、`fetchMe()`、`logout()`、`reset()`；token 持久化在 `localStorage`（`trade_token`）。
- 路由守卫：`meta.requiresAuth` 未登录跳 `/login?redirect=`；`meta.roles` 为 `['ADMIN']` 时，`roles` 不含 `ADMIN` 跳 `/403`；刷新后 store 只有 token，守卫里 `fetchMe()` 补拉用户与权限，失败即视为 token 失效。

## 8. 边界与明确不做的事

| 不做 | 原因 |
|---|---|
| 真实微信/支付宝对接 | 没有商户资质；`/api/pay/mock/{orderNo}` 是本地模拟网关，签名与回调链路真实，网关是假的 |
| 购物车、多商品合并下单 | 秒杀是“单品单件”模型，凑单会引入拆单与优惠计算，超出本轮范围 |
| 分库分表 / 库存分桶 | 单 SKU 库存 < 1000、目标 QPS 500，单 key 足够；分桶方案在文档里写明“知道瓶颈但当前量级不解决” |
| 分布式事务（Seata） | 秒杀走最终一致：Redis 挡流量、DB 是真相、关单与对账收敛 |
| refresh token | 2 小时 TTL + 前端 401 跳登录够用；refresh 会引入轮换与重放防护 |
| Redisson / Caffeine | 锁场景简单（SETNX+Lua 够用）；本地缓存多实例不一致 |
